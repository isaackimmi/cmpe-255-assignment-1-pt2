# Data-science robustness review — Project 01

Review scope: target construction, temporal evaluation, leakage, preprocessing, baseline choice, metrics, reproducibility, fallback-data validity, and UI claims. Reviewed without changing source code. Paths below are relative to this project root.

## Overall assessment

The checked-in default run is a useful deterministic synthetic smoke experiment, not evidence of real NYC taxi performance. Its basic modeling logic is coherent: `trip_duration` is the target, the listed features are request-time features, scaling is fit on the training partition, and the reported test metrics are calculated in seconds after inverse-transforming the log target. However, the temporal guarantee advertised by the README/UI is not enforced for CSV inputs, and the documented data-cleaning pipeline is materially different from the implementation. These are the main blockers to treating a real-CSV run as a valid chronological evaluation.

## Findings

### [P1] CSV inputs are not actually sorted before the claimed chronological split

Evidence:

- `run_experiment.py:24-25` reads a CSV and preserves its row order.
- `run_experiment.py:12-22` sorts only rows generated by the synthetic fallback.
- `run_experiment.py:68-69` applies `data[:cut]` / `data[cut:]` without sorting or checking timestamps.
- The chronological guarantee is stated in `README.md:18`, `README.md:61`, and `index.html:33,117`.
- A direct probe using a reversed 1,000-row CSV produced a training boundary of `2016-01-20 11:17:00` followed by a test start of `2016-01-20 11:02:00`; the boundary assertion `max(train pickup) <= min(test pickup)` was false.

Impact: a caller can obtain a test set containing earlier trips than the training set. This can place future observations in training and invalidate the intended forward-in-time estimate. The checked-in fallback numbers are sorted and do not demonstrate this failure, but the real-CSV path is not protected.

Concrete fix: parse timestamps into a normalized datetime (including timezone handling), sort the cleaned rows by that value immediately before splitting, and record the split cutoff in `metrics.json`. Add a hard assertion/test that every training timestamp is less than or equal to every test timestamp, or use an explicit date cutoff and fail on violations.

### [P1] The implemented cleaning does not match the documented cleaning and has weak real-data validation

Evidence:

- `README.md:17` says the pipeline removes invalid coordinates and extreme duration outliers using training-set quantiles.
- `run_experiment.py:27-40` converts fields and retains a row only when `y > 0` and `dist < 100`. It does not calculate quantiles, enforce latitude/longitude ranges, check finite values explicitly, or apply a documented duration upper bound.
- `run_experiment.py:39` silently discards conversion failures with `except (...): pass`, and `metrics.json` records only the final row count, not input rows or drop reasons.

Impact: malformed or implausible rows can enter a real run, while parse failures disappear without an audit trail. Extreme positive durations can still affect the fit. The `dist < 100` condition is a route-distance cap, not a general coordinate-validity check or target-outlier policy.

Concrete fix: validate the required schema; require finite values and valid coordinate ranges; define an explicit NYC/domain policy and a pre-specified duration policy; count and report drops by reason; and fail or warn when the drop rate exceeds a threshold. If statistical thresholds are used, fit them on training data only and document how test/inference rows are handled.

### [P2] The evaluation is too weak to support the model-selection language

Evidence:

- `run_experiment.py:69-70` compares only one constant training-median baseline with one regularized linear model on one 80/20 holdout.
- `validate.py:11` checks only that model MAE is below baseline MAE, even though `README.md:51` says the model should beat the baseline on both MAE and RMSE.
- There is no rolling/expanding temporal evaluation, uncertainty interval, or stronger time-aware naive baseline such as a recent or hour-conditioned median.

Impact: the median is a valid minimal sanity check, but it is a weak benchmark for a time- and route-dependent target. A single holdout can make the reported improvement unstable, and the validation script could pass while RMSE regresses. The current artifact does happen to recompute to MAE `82.045` and RMSE `102.688`, versus baseline MAE `147.927` and RMSE `184.250`.

Concrete fix: retain the global median as a floor, add a recent/seasonal or route-time naive baseline, evaluate across multiple chronological folds, and assert/recompute every published metric from the prediction file, including RMSE and R².

### [P2] `feature_importance.csv` is not a comparable feature-importance ranking

Evidence:

- `run_experiment.py:43-50` standardizes features for fitting but writes `abs(weight / scale)` as `importance`.
- `run_experiment.py:73` labels and sorts those values as `feature_importance.csv`.

Impact: the output is the absolute coefficient per original feature unit, so magnitudes are not comparable across miles, degrees, counts, hours, and binary indicators. Correlated coordinate/delta features also make individual coefficient attribution unstable. Calling this file feature importance can lead to incorrect conclusions about what the model learned.

Concrete fix: either label the artifact as raw-unit coefficients, use absolute standardized coefficients for a descriptive linear-model ranking, or compute permutation importance on held-out chronological data. Report grouped/ correlated feature effects where appropriate.

### [P2] Reproducibility metadata is incomplete outside the default fallback run

Evidence:

- `run_experiment.py:7,13` makes the fallback deterministic with seed `255`.
- `run_experiment.py:67-74` does not persist the seed, sample size, timestamp cutoff, feature list, model hyperparameters, Python version, or an input-data hash. It also overwrites the same output files for every run.
- The `--sample-size` argument is documented alongside `--input` in `README.md:30-32`, but `run_experiment.py:67-68` ignores `sample-size` whenever an input CSV is supplied.

Impact: the no-argument fallback is reproducible in practice, but a real-data result cannot be reconstructed from the checked-in metadata alone, and the documented CLI suggests an option that has no effect in the CSV path.

Concrete fix: record the full run configuration, split cutoff, source path plus content hash, input/cleaned counts, model coefficients or a model artifact, and runtime/version information. Reject or remove the irrelevant `--sample-size` option when `--input` is present, or define and implement its intended behavior.

### [P2] Two UI improvement claims remain hard-coded for non-default runs

Evidence:

- `index.html:43` hard-codes `44.5% below baseline`; `index.html:68` hard-codes `44.5%` again.
- `app.js:17-34` dynamically updates only elements with `data-metric` and never updates those two text nodes. `index.html:39` also contains a static accessibility label stating model MAE 82 seconds.
- The UI does load `outputs/metrics.json` dynamically (`app.js:84-92`), so running the experiment on a different CSV can change the metric cards while leaving the hero/callout claims stale.

Impact: after a real CSV run, the page can display internally inconsistent results and imply the default synthetic improvement still applies.

Concrete fix: put the hero percentage, callout percentage, and accessible label behind data attributes updated from the loaded metrics, or explicitly label those values as the checked-in fallback result.

### [P3] The illustrative estimator is directionally related to, but not identical to, the fallback generator

Evidence:

- `run_experiment.py:19-20` generates duration using an approximate distance formula, rush-hour/passenger effects, and Gaussian noise, with no weekend term.
- `app.js:68-72` uses haversine distance, omits noise, and adds a `-12` second weekend adjustment.
- The UI does disclose this limitation in `index.html:80,106`, calling it illustrative and not a model/production prediction.

Impact: the disclosure prevents this from being a serious modeling-validity issue, but users cannot reproduce the displayed what-if estimate from the Python fallback equation exactly.

Concrete fix: share one explicitly named illustrative formula or state that the browser control is only a qualitative visualization and list its deliberate differences.

### [P3] README contains stale model terminology

Evidence: `README.md:56` says “Random forests are a practical baseline,” but the implementation contains a median baseline and a regularized linear model (`run_experiment.py:45-50,69`).

Concrete fix: remove the random-forest statement or implement and evaluate that model; keep the README’s method, limitations, and artifacts synchronized with the executable pipeline.

## Sound aspects / no issue found

- Target construction is explicit: `run_experiment.py:37` reads `trip_duration`; `id` is not used as a predictor.
- The features used by the model are available at pickup/request time. No direct target leakage was found in `run_experiment.py:10,27-38`.
- Standardization parameters are computed from training rows only (`run_experiment.py:43-44`), and the log target is a reasonable choice for a positive, right-skewed duration target (`run_experiment.py:45`).
- MAE and RMSE are reported in original seconds after prediction is transformed back with `expm1`; an independent recomputation from `outputs/predictions.csv` matched `82.045` and `102.688`.
- The fallback is clearly identified as deterministic synthetic NYC-like data in `README.md:11,47,51`, `index.html:75,106`, and `outputs/metrics.json:2`; its results should remain labeled as a pipeline demonstration rather than a real-world benchmark.
